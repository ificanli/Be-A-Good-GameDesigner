# 数值设计不是填表：从目标到回滚的完整闭环

> 本文受到 zsc 的《游戏数值策划完全教程》启发，但不是原教程的章节缩写。本文重新组织其问题域，并结合系统设计方法，凝练出一套可用于实际项目的数值工作框架。
>
> 原教程与核验说明见：[[../99_资料来源/游戏数值策划完全教程-资料卡|《游戏数值策划完全教程》资料卡]]。

## 一、数值设计到底在设计什么

数值设计表面上处理攻击力、经验、掉率、价格和评分，实际上处理的是四种关系：

1. **玩家行动与结果的关系**：一次选择能换来什么，失败会损失什么。
2. **投入与成长的关系**：时间、技巧、风险、货币如何转化为能力和内容进度。
3. **系统之间的关系**：战斗、装备、经济、匹配和运营如何互相影响。
4. **规则与体验的关系**：同一组数学结果，玩家是否能理解、相信并接受。

所以，数值设计不是“找一个看起来合理的数字”，而是：

> 用可计算、可验证、可调整的模型，将目标体验转化为规则，并控制它在不同玩家、不同阶段和不同版本中的后果。

一张表能装数字，但装不下设计目标、适用边界、玩家行为和回滚方案。只会填表的数值系统，通常会在上线后用玩家当计算器。

---

## 二、完整闭环：六个阶段

```text
目标定义 → 系统建模 → 参数标定 → 离线验证 → 发布观测 → 学习迭代
    ↑                                                        ↓
    └────────────── 版本记录、迁移与回滚 ──────────────────┘
```

六个阶段缺少任何一个，都会留下典型风险：

- 没有目标：数字能算，却不知道什么叫“好”。
- 没有模型：参数互相打补丁，最后没人知道因果关系。
- 没有标定：公式很漂亮，但节奏和量级不符合游戏。
- 没有验证：平均值正常，极端 Build 和坏运气把系统撕开。
- 没有观测：上线后只看到玩家骂，不知道哪里出了问题。
- 没有回滚：发现问题也不敢改，因为玩家资产已经被污染。

下面逐一展开。

---

## 三、阶段一：先定义目标，不要先写公式

### 3.1 把形容词改成可观察结果

“战斗要爽”“成长要平滑”“掉落要惊喜”都不是可执行目标。它们至少要被拆成：

- 玩家要做什么决策？
- 期望出现什么行为？
- 目标体验如何被观察？
- 哪些后果绝对不能出现？

例如，“Boss 战要紧张但公平”可以转化为：

- 玩家能从前摇识别主要攻击；
- 首次挑战允许犯若干次普通错误；
- 失败后能明确指出至少一个可改进动作；
- 高水平玩家可通过操作缩短战斗，但不能跳过全部机制；
- 低概率事件不能单独导致满血角色死亡。

这些描述之后，才轮到生命值、伤害、前摇、资源恢复和概率。

### 3.2 为系统定义三类指标

每个数值系统至少需要三类指标：

| 类型 | 回答的问题 | 示例 |
|---|---|---|
| 结果指标 | 目标体验是否发生 | 通关率、有效 Build 数、经济购买力 |
| 输入指标 | 为什么会发生 | DPS、资源产出、匹配分差、失败原因 |
| 护栏指标 | 是否用坏方式达成 | 退出率、坏尾部、付费投诉、等待时间 |

结果指标上涨，不一定是好事。通关率可以通过合理学习提高，也可以通过偷偷降低敌人命中率提高。后者数字漂亮，玩家却可能感到系统虚假。

### 3.3 写出不变量

不变量是版本改变时尽量需要保持的关系，例如：

- 同等投入下，旧资产不能无理由大幅贬值；
- 坦克的有效生存时间应高于输出角色；
- 同段位玩家的预期胜率应接近；
- 货币不能在无成本闭环中无限增殖；
- 属性压缩后，相对强弱和关键阈值尽量不变。

没有不变量，所谓“平衡调整”很容易变成每次都重新发明公平。

## 四、阶段二：把系统画出来，再把公式写出来

### 4.1 先分清存量、流量和转换

数值系统最基本的三个对象是：

- **存量**：玩家当前拥有多少，如金币、经验、生命、卡牌。
- **流量**：单位时间或单位行为增加/减少多少。
- **转换**：一种资源如何变成另一种资源或能力。

例如经济系统可以先写成：

$$
\Delta M = Sources - Sinks
$$

但这只是起点。真正需要继续追问的是：

- 谁在产出，谁在消耗？
- 发生在哪个玩家阶段？
- 资源是否可以交易？
- 存量分布是否集中在少数玩家？
- 产出和消耗是否拥有相同的时间尺度？

全服总量稳定，也可能掩盖新玩家贫困和老玩家巨额囤积。

### 4.2 标出反馈回路

数值平衡最危险的往往不是单条公式，而是回路。

典型正反馈：

```text
领先 → 获得更多资源 → 属性更强 → 更容易继续领先
```

典型负反馈：

```text
落后 → 获得有限追赶机会 → 缩小差距 → 恢复竞争
```

正反馈创造成长感和决策价值，但过强会形成滚雪球；负反馈维持悬念，但过强会让前期努力失去意义。问题不是选哪一个，而是控制回路的增益、延迟、上限和触发条件。

### 4.3 明确计算顺序和边界

同样的参数，在不同计算顺序下可能产生完全不同的系统：

```text
基础值 → 固定加成 → 百分比加成 → 场景修正 → 防御结算 → 取整
```

设计文档必须明确：

- 加法组与乘法组；
- 上限、下限和软上限；
- 快照还是动态计算；
- 取整发生在哪一步；
- 客户端与服务端谁是权威；
- Buff 的刷新、覆盖和叠层顺序。

大量“数值 Bug”其实不是公式错，而是时序、单位或实现约定不一致。

## 五、阶段三：参数标定——从体验锚点反推数字

### 5.1 先选锚点

不要同时凭感觉填写几百个参数。先确定少量体验锚点：

- 标准角色击败标准敌人的目标时间；
- 玩家每分钟可做的有效决策次数；
- 一次普通失误损失多少生存资源；
- 每个成长阶段持续多久；
- 一次奖励相当于多少分钟常规游戏；
- 极端坏运气最多持续到哪里。

锚点确定后，其他数值围绕它推导。

### 5.2 曲线是节奏，不是数学装饰

常见曲线并没有天然优劣：

- 线性适合稳定、可预测的增长；
- 多项式适合逐渐拉长阶段；
- 指数适合跨数量级成长，但很容易失控；
- 分段函数适合服务不同生命周期；
- 对数或双曲函数适合实现边际递减。

选择曲线前应问：玩家在这一阶段要停留多久？增长是为了打开新策略，还是只为了提高数字？旧内容需要保留多久？

### 5.3 不只比较数值，还要比较机会成本

一个选项的真实成本可能包括：

- 货币；
- 时间；
- 资源槽位；
- 冷却窗口；
- 风险暴露；
- 放弃其他 Build 的机会；
- 学习和操作负担。

如果只给所有属性计算面板战力，却忽略触发条件、覆盖率和机会成本，战力评分就会非常擅长一本正经地误导玩家。

## 六、阶段四：验证——平均值只是开始

### 6.1 最少做四层验证

#### 第一层：合法性检查

- 概率是否在 $[0,1]$；
- 概率和是否正确；
- 成本是否非负；
- ID 和引用是否存在；
- 等级和区间是否连续；
- 单位是否一致。

#### 第二层：黄金样例

固定角色、目标、配置和随机种子，手工计算一组可验证结果。每次修改后都跑一遍，定位公式在哪一步首次分叉。

#### 第三层：边界与极端组合

测试：

- 全部加成叠满；
- 最低和最高等级；
- 零资源、满资源；
- 极端暴击、攻速、减伤或冷却；
- 最差运气和连续失败；
- 新旧系统交界点。

#### 第四层：模拟与敏感度分析

通过批量计算或蒙特卡洛模拟观察：

- 均值、中位数、方差和分位数；
- 参数变化 1% 会让结果变化多少；
- 哪些变量真正控制结果；
- 哪些 Build 在不同场景中占优；
- 最坏尾部是否仍可接受。

### 6.2 期望相同，体验可以完全不同

两个掉落方案可能拥有相同数学期望：

- A：每局稳定获得 10；
- B：九局获得 0，一局获得 100。

它们的资源总量相同，但学习、情绪、留存和风险感受完全不同。因此概率系统至少要同时看：

- 期望；
- 方差；
- 达成目标所需次数的分布；
- P50、P90、P99；
- 保底前的最坏体验；
- 玩家是否理解概率和进度。

### 6.3 平衡不是全局胜率等于 50%

全局平均值会混合：

- 技能段；
- 地图；
- 队伍和对手组合；
- 使用者熟练度；
- 版本阶段；
- 新手与老玩家。

一个角色总体胜率上涨，可能只是高水平使用者占比增加。先分层，再讨论因果。否则数据越多，错得越有统计气质。

## 七、阶段五：发布——数值改动也是一次软件发布

### 7.1 配置必须可追溯

每次发布应能回答：

- 改了什么；
- 为什么改；
- 谁审核；
- 对哪些系统和玩家生效；
- 使用哪个配置版本；
- 模拟结果是什么；
- 出问题如何止血。

版本评审不能只看文本差异。把技能倍率从 1.2 改到 1.3 是文本差异；它使标准 Build DPS 提升多少、爆发尾部改变多少、哪些装备因此翻身，才是语义差异。

### 7.2 灰度、开关和回滚要提前设计

安全发布至少考虑：

- 是否可配置关闭；
- 是否能按服务器或玩家群灰度；
- 新旧逻辑能否影子对比；
- 玩家资产变化是否有账本；
- 迁移脚本是否幂等；
- 回滚规则、配置和数据分别怎么处理。

“上线后看情况”不是方案，那是给事故预约档期。

### 7.3 迁移的核心是保护关系

数值压缩、货币合并、装备重做和等级调整都不是简单乘除法。迁移要保护：

- 相对强度；
- 累计投入；
- 稀缺性；
- 已作出的付费或时间承诺；
- Build 功能；
- 玩家可理解性。

无法可逆映射时，必须保留来源明细和迁移账本，而不是在回滚时从新值猜旧值。

## 八、阶段六：用数据学习，但不要向指标投降

### 8.1 从决策反推数据

先问要做什么决策，再决定采集什么事件。每个指标应明确：

- 对象；
- 分母；
- 时间窗口；
- 去重方式；
- 过滤条件；
- 配置版本；
- 负责人。

没有口径的“DAU”“胜率”“资源产出”只是三个看起来很忙的词。

### 8.2 异常不等于根因

发现金币净流入上涨，只说明现象。完整诊断流程应是：

1. 检查埋点、重复数据和口径；
2. 确认异常发生在哪些人、渠道和版本；
3. 分解来源和消耗；
4. 提出多个竞争解释；
5. 用对照、时间变化或实验排除解释；
6. 修复后继续观察是否恢复。

模型可以帮助排序异常，但不能自动宣布“谁是凶手”。

### 8.3 实验需要护栏和长期视角

A/B 测试不只是看显著性。还要检查：

- 随机化单位是否正确；
- 玩家之间是否互相污染；
- 是否覆盖完整活动和生命周期；
- 是否提前定义主要指标；
- 是否存在多重检验；
- 短期收益是否伤害长期生态；
- 效果是否只来自某个脆弱群体。

统计显著不等于设计值得上线。

## 九、数值设计的五条总原则

### 原则一：先定义体验，再选择模型

公式服务目标，不要让玩家替公式服务。

### 原则二：既看平均，也看分布和坏尾部

平均玩家通常不存在，真正受伤的是某一类具体玩家。

### 原则三：既看单系统，也看反馈回路和跨系统传播

局部平衡可能制造全局灾难。

### 原则四：既设计成功路径，也设计失败、退出和恢复路径

公平感很大一部分来自失败是否可理解、损失是否可控、退出是否被尊重。

### 原则五：任何线上数值都必须可解释、可观测、可回滚

不能安全改变的系统，迟早会因为不敢改变而腐烂。

## 十、一页式数值方案模板

### 1. 设计问题

当前体验哪里有问题？证据是什么？

### 2. 目标与护栏

要改善什么？绝不能恶化什么？

### 3. 系统边界

涉及哪些存量、流量、转换、玩家群和时间尺度？

### 4. 模型与假设

公式、单位、计算顺序、上下限和关键假设是什么？

### 5. 体验锚点

目标 TTK、成长时长、回本时间、奖励密度或最坏等待是多少？

### 6. 验证计划

黄金样例、边界测试、模拟、分层和试玩分别验证什么？

### 7. 影响分析

会传播到哪些系统、资产、内容和玩家群？

### 8. 发布计划

配置版本、评审、灰度、监控和告警是什么？

### 9. 迁移与回滚

旧资产如何处理？触发什么条件时回滚？如何对账？

### 10. 学习记录

结果是否支持原假设？下一轮保留、修改或放弃什么？

---

## 结语

好的数值系统并不是所有数字都“完美平衡”。它应让玩家理解行动与结果的关系，让不同选择在明确条件下成立，让团队知道一个参数为什么存在，也让版本变化之后仍能追溯、验证和修复。

数值策划真正交付的不是一张 Excel 表，而是一条证据链：

> 目标有定义，模型有假设，参数有依据，结果可复现，发布可观测，事故可回滚。

做到这一步，数字才不只是数字，而是可控的游戏体验。
