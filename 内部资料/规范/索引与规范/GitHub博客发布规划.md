# GitHub 博客发布规划

## 最终目标

将本目录发布为一个公开的游戏设计知识库博客：

- 以 Markdown 作为唯一内容源
- 使用 Git 记录每次修改
- 通过 GitHub Pages 自动发布
- 支持中文阅读、全文搜索、标签、目录和文章互链
- 持续收集外部资料，并加工为原创方法论、案例拆解和设计模板

## 推荐技术方案

### 首选：Quartz

适合当前项目的原因：

- 原生支持 Markdown 知识库结构
- 支持双向链接、标签、目录和全文搜索
- 适合大量相互引用的研究笔记
- 可以部署到 GitHub Pages
- 不需要先搭建复杂后端

### 备选方案

- **MkDocs Material**：文档导航和版本化更强，适合教程型资料库。
- **Docusaurus**：适合正式文档站和未来增加组件、版本、搜索服务。
- **Astro/Starlight**：适合高度定制视觉风格，但初期维护成本更高。

## 内容发布规范

### 公开范围采用白名单

GitHub 仓库可以保存知识库文件，但 GitHub Pages 的 `docs/` 只发布明确列入白名单的正式文章。不得因为文件已进入仓库，就默认复制到网站。

允许公开：

- 已选定供读者阅读或审阅的正式主题文章；
- 网站首页及公开文章必需的图片、样式和脚本。

默认不公开：

- `00_索引与规范/` 中的内部规范、待判断与归档；
- `98_待整理资料/` 中的原始资料、OCR、处理记录和覆盖状态；
- 工作脚本、验证代码和中间提取文件；
- 临时凝练稿、章节地图、内部 README 和资料登记卡；
- 仅用于作者核验、不能独立服务读者的来源索引。

发布使用 `python scripts/build_public_site.py`。脚本必须清理白名单之外的 `docs/` 文件，并将公开文章中指向内部资料的 Wiki 链接降级为普通文字。新增文章不能靠手工复制进入网站，必须先加入白名单和首页入口。

### 文件规范

- 文件名使用清晰的中文标题，避免特殊符号。
- 每篇正式文章使用 YAML Frontmatter。
- 资料原文、个人判断和案例观察分开写。
- 外部内容只做合理引用和摘要，不整篇复制。
- 图片尽量使用自制图、可商用素材或明确授权素材。
- 失效链接和过期内容标记为 `需复查`。

### 推荐 Frontmatter

```yaml
---
title: 核心循环设计方法
description: 从玩家动词、资源和反馈分析游戏的核心循环
tags:
  - 基础理论
  - 玩法机制
status: draft
source_type: original
created: 2026-02-21
updated: 2026-02-21
---
```

字段说明：

- `title`：页面标题
- `description`：搜索摘要
- `tags`：主题标签
- `status`：`draft` / `review` / `published`
- `source_type`：`original` / `research` / `case-study` / `template`
- `created`、`updated`：创建和更新时间

## 建议的公开内容层级

### 第一层：入口页

- 知识库总索引
- 主题分类
- 术语表
- 阅读路线
- 关于本站
- 资料来源与引用说明

### 第二层：原创方法论

把多个来源加工成可复用的中文文章，例如：

- 核心循环设计
- 有意义的选择
- 战斗遭遇设计
- 资源 Source/Sink
- Teach-Test-Twist
- 试玩问题诊断

### 第三层：案例拆解

分析具体游戏，但必须写清楚设计目标、机制、行为、体验、代价和适用边界。

### 第四层：资料卡与阅读笔记

记录论文、书籍、GDC、知乎、Indienova 和开发者文章，注明核验状态，不把来源摘要伪装成原创结论。

## GitHub 仓库建议结构

```text
游戏设计逻辑/
├─ content/                 # 对外发布的文章
├─ sources/                 # 外部资料卡与来源索引
├─ templates/               # 文章、案例、资料卡模板
├─ drafts/                  # 尚未发布的草稿
├─ assets/                  # 图片、图表和附件
├─ README.md
└─ quartz.config.ts         # 使用 Quartz 时由框架提供
```

当前目录可以先保持主题文件夹结构；正式接入 Quartz 时，再决定是否迁移到 `content/`，避免过早改动导致内部链接失效。

## 发布前检查

- [ ] 标题、摘要和标签完整
- [ ] 内部链接可访问
- [ ] 外部链接可访问
- [ ] 原文观点与个人判断已区分
- [ ] 没有未经授权的大段转载
- [ ] 图片和字体具备使用权限
- [ ] 文中公式、表格和代码在网页端显示正常
- [ ] 手机端阅读正常
- [ ] 草稿没有被公开构建
- [ ] `docs/` 中只有公开白名单文件，没有待判断、内部规范、资料登记、OCR 或工具脚本
- [ ] 首页每篇入口都能打开，且不存在未列首页却能通过直链访问的内部文件
- [ ] 正式文章指向内部资料的链接已在公开构建中降级，不会产生泄露或 404
- [ ] 开头从实际设计问题进入，不用抽象定义劝退非专项读者
- [ ] 每节先解释方法，再给公式或案例
- [ ] 公式说明了如何支持设计决策，不只罗列变量
- [ ] 正文没有突然插入来源介绍，来源统一放在文末
- [ ] 数值同行能直接使用，非数值策划也能读懂逻辑

## 推荐推进顺序

1. 先整理内容和内部链接，不急着装框架。
2. 为正式文章补 Frontmatter。
3. 先完成 5—10 篇高质量原创文章。
4. 创建 GitHub 仓库并提交初始版本。
5. 接入 Quartz 和 GitHub Actions。
6. 开启 GitHub Pages。
7. 发布后再优化主题、搜索和导航。
