# 游戏设计文章写作与审稿标准

## 1. 目标

本库文章应让有一定游戏设计基础的读者在第一次阅读时完成三件事：

1. 理解文章正在解决哪个设计问题；
2. 看懂结论如何从规则、案例或数据中推出；
3. 知道自己可以怎样使用、验证或反驳这个方法。

文章不能只做到“信息正确”。如果读者需要反复回看术语、自己补齐推导，或看完只记住一串分类，文章仍未完成。

## 2. 先确定文章承担的任务

每篇文章以一种主要任务为主：

- **解释**：帮助读者理解一个设计问题为什么出现，以及不同方案的取舍。
- **操作指南**：帮助读者完成一次建模、评审、验证或决策。
- **参考资料**：供读者查询公式、字段、检查项和边界。
- **案例复盘**：还原设计意图、实现结果、证据和结论变化。

本库主文章通常是“解释”或“操作指南”。公式表、检查表和字段表可以作为文内辅助，也可以拆成独立参考页。不要把四种任务全塞进一篇文章，否则正文会在讲道理、下指令、列百科和讲故事之间不断跳转。

## 3. 文章结构

### 3.1 开头先建立阅读问题

开头用一个具体工作场景说明文章为何存在。读者应在前三段内知道：

- 当前要做什么决策；
- 常见做法为什么不够；
- 本文会提供什么方法。

不要先给宏大定义，也不要用口号代替问题。例如，与其写“玩法融合的本质是共享决策”，不如先描述一个具体困境：两个系统已经交换资源，试玩者却仍觉得自己在轮流玩两款游戏。然后再说明需要检查的关系。

### 3.2 每节只推进一个主要判断

一个完整小节通常包含：

1. **局面或问题**：读者正在面对什么；
2. **判断**：本节主张什么；
3. **理由**：为什么成立；
4. **例子或反例**：在具体规则中会怎样表现；
5. **边界**：什么时候不能直接套用；
6. **动作**：读者下一步怎样检查或使用。

这些内容不必机械写成六个标题，但不能只剩“结论 + 清单”。

### 3.3 按信息依赖排序

术语出现前先解释对象，公式出现前先说明用途，检查表出现前先讲判断依据。后一节依赖前一节的概念时，应让读者能顺着文章自然获得这些前置知识。

不要为了目录整齐而按“定义—分类—特点—总结”的百科顺序写。游戏设计文章更适合按一次真实决策的顺序组织。

## 4. 句子与段落

### 4.1 一句话承担一个主要判断

条件、动作和结果可以在同一句中，但不能并列两个需要分别证明的结论。中文正文超过约 60 个字符时，应检查是否塞入了多个判断；这是审查信号，不是强制截断线。

### 4.2 长短句要有节奏

短句用于落下结论。较长的句子用于连接条件、原因和后果。不要把所有句子削成同样长度，也不要连续多段都采用“定义一句、解释一句、总结一句”的机械节奏。

### 4.3 一个段落完成一次推进

段落应让读者从一个已知位置走到一个新结论。若段落同时定义概念、比较方案、讲案例并提出检查项，应拆开。若连续三个段落都只有一两句抽象判断，应补充具体局面或合并推导。

### 4.4 使用同行会说的话

优先使用准确、常见的业务语言。术语只有在能缩短后续沟通时才命名。不要发明“高阶抓手”“价值闭环”一类看似专业、实际要求读者再次翻译的词。

同一对象在全系列中使用同一名称。不要为了避免重复而轮换同义词。

## 5. 案例、公式与清单

### 5.1 案例必须承担证明任务

案例需说明：

- 当时有哪些规则和约束；
- 玩家具体做了什么；
- 观察到了什么结果；
- 这个结果支持或反驳哪条判断；
- 证据仍缺什么。

只点名游戏或项目，不算案例。案例也不能替代方法解释。

### 5.2 公式要连接设计决策

公式前说明它解决什么问题。公式后解释变量变化会怎样影响结果，以及设计者根据结果应做什么。公式如果只展示计算而不支持决策，应移入参考页或删除。

### 5.3 清单用于执行，不用于代替正文

正文先说明判断逻辑，再用清单帮助复查。连续出现大量列表时，要检查文章是否退化成演讲提纲。列表项应保持同一层级和语法结构。

## 6. 分轮审稿

完成草稿后，不要从头到尾边读边随手润色。至少分五轮处理：

### 第一轮：任务与结构

- 文章的主要任务是否明确？
- 每节是否在回答同一个上位问题？
- 章节顺序是否符合信息依赖？
- 是否混入可以拆成参考页或案例页的内容？

### 第二轮：推导完整性

- 每个关键结论是否有理由？
- 理由是否有规则、数据、案例或反例支持？
- 是否把相关性写成因果关系？
- 是否把项目经验写成普遍规律？

### 第三轮：阅读负担

- 术语是否在使用前解释？
- 长句是否同时承担多个判断？
- 段落是否一次推进太多内容？
- 清单和抽象名词是否过密？
- 是否有具体局面帮助读者建立画面？

### 第四轮：语言与节奏

- 删除无信息的过渡语和套路句；
- 合并重复内容；
- 变化句长，但不故意追求花哨；
- 朗读容易卡住的句子；
- 保留作者明确判断，不把文章磨成无立场说明书。

### 第五轮：事实与发布

- 核对公式、数字、版本和案例；
- 检查来源与证据等级；
- 确认争议项已经交由维护者判断；
- 检查内部链接、网站显示和批注定位。

## 7. 自动工具的职责

自动工具只处理或提示机械问题：

- `内部资料/工具/文章可读性审查.py`：报告句长、列表密度、重复句首、模板句和抽象词密度；
- [lint-md](https://github.com/lint-md/lint-md)：检查中文 Markdown 格式；
- [AutoCorrect](https://github.com/huacnlee/autocorrect)：统一中英文空格和标点；
- [Vale](https://github.com/vale-cli/vale)：以后用于执行本库自定义文风规则；
- [AlphaReadabilityChinese 2.0](https://github.com/corpustalk/AlphaReadabilityChinese2.0)：可用于专题性比较，不作为文章是否合格的裁判。

平均句长、词汇复杂度和语义连贯分数只能指出风险。工具无法判断一个案例是否证明了结论，也无法判断删掉一个前提是否改变设计含义。

## 8. 发布门槛

正式发布前，编辑者应能回答：

- 用一句话说明这篇文章帮助读者完成什么；
- 指出全文最重要的三个判断及其证据；
- 指出一个不能直接套用本文方法的场景；
- 指出读者看完后可以执行的具体动作；
- 解释为什么每个主要案例留在文中。

答不出来时，先改结构，不要继续修标点。

## 9. 采用的外部方法

本标准吸收并本地化以下公开方法：

- Diátaxis：区分教程、操作指南、参考资料和解释；
- Google Developer Documentation Style Guide：面向读者、条件前置、标题表达观点；
- ASD-STE100 与 Global English：降低句法歧义和单句负担；
- `cursor/plugins@technical-writing` Skill：分层审查、控制术语、变化语言节奏；
- 中文技术文档写作风格指南：中文技术文档的结构和表达规范。

这些方法用于建立审稿步骤，不会机械套用英语可读性公式到中文文章。
