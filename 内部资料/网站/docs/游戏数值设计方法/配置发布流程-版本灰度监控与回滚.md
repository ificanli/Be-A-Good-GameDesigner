# 配置发布流程：版本、灰度、监控与回滚

数值配置进入线上后会影响战斗、经济和玩家资产。发布流程需要保证改动可识别、可验证、可观测，并在异常时安全停止或回退。

## 1. 版本化

每次发布记录配置版本、适用客户端和服务器、变更人、审批人、变更原因和影响范围。运行日志携带配置版本，否则无法解释跨版本数据。

配置、规则代码和迁移脚本分别版本化，并记录兼容关系。只保存最终 Excel 文件不足以重建线上状态。

## 2. 发布前门禁

执行 Schema、引用、范围、概率、黄金样例、边界、模拟和资产迁移检查。高风险改动还需生产快照演练、性能测试和客户端兼容检查。

门禁失败必须阻止发布，不应依赖“这次先手动确认”。临时豁免要记录原因、风险和补测计划。

## 3. 差异评审

不仅比较单元格，还要生成语义差异：哪些角色伤害变化、哪些玩家完成时间变化、货币净流量变化、哪些资产需要迁移。大量自动生成行的差异应汇总为业务指标。

评审材料包含改动目的、影响路径、黄金样例、模拟结果、监控指标和回滚方案。

## 4. 灰度

按内部、测试服、少量服务器或玩家群逐步扩大。灰度分组要考虑社交、匹配和交易污染。提前定义继续、暂停和回滚阈值，不能上线后临时挑选对自己有利的指标。

灰度时间应覆盖目标行为周期。每日养成和周活动需要不同观察窗口。

## 5. 监控

同时监控系统健康、目标指标和护栏指标。战斗改动观察 TTK、胜率和异常伤害；经济改动观察产销、库存和套利；概率改动观察实际概率、保底和投诉。

监控按配置版本、玩家层和模式分层，避免新旧配置混合后平均正常。

## 6. 回滚

规则、配置和玩家数据回滚分开。配置回滚不一定能撤销已经产生的资产；数据回滚也不能覆盖发布后玩家的合法进展。使用迁移账本和补偿事务处理不可逆结果。

回滚方案明确触发人、执行顺序、兼容窗口、数据对账和玩家通知。定期演练，不把回滚停留在文档里。

## 7. 事故复盘

记录时间线、影响范围、触发条件、检测缺口、处置和长期修复。复盘目标是更新门禁、监控和回归集，而不是只追究谁填错数字。

## 8. 发布清单示例

```text
冻结输入与版本
→ 自动校验
→ 黄金样例与批量回归
→ 语义差异评审
→ 生产快照演练
→ 灰度
→ 指标和护栏监控
→ 全量或回滚
→ 对账与复盘
```

## 9. 事故示例

若掉落权重错误导致稀有物多发，简单回滚配置只能阻止继续产出，不能处理已经获得和交易的资产。处置需冻结相关交易、统计来源、评估是否回收或保留、执行补偿并对账。方案取决于影响和玩家信任，不能默认整库回档。

## 发布前检查

- [ ] 配置、代码和迁移是否分别版本化？
- [ ] 自动门禁能否真正阻止错误发布？
- [ ] 是否生成业务语义差异？
- [ ] 灰度是否避免社交和市场污染？
- [ ] 回滚是否处理已产生的玩家资产？
