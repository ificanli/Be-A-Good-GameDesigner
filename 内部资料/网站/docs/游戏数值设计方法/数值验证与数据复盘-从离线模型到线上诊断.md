# 数值验证与数据复盘：从离线模型到线上诊断

数值表能够算出结果，不代表结果符合设计目标。公式可能写错，输入可能过期，模型可能遗漏玩家行为，实机实现也可能与策划表不同。上线数据则会进一步暴露参与率、操作方式和消费策略与设计假设之间的偏差。

验证工作的目的，是为每类结论找到合适证据，并在结果异常时确定问题位于哪一层。单个平均值或一次试玩都不足以证明系统成立。

## 1. 建立验证链

数值方案可以按五层验证：

```text
公式与配置检查
→ 黄金样例
→ 批量模拟与分布
→ 实机试玩与日志对账
→ 线上数据与版本复盘
```

每层解决的问题不同：

| 层级 | 主要问题 |
|---|---|
| 公式与配置 | 公式、单位、引用、边界和概率是否正确 |
| 黄金样例 | 典型输入能否得到人工确认的结果 |
| 批量模拟 | 随机、策略和玩家分层会形成什么分布 |
| 实机试玩 | 动作、界面、AI 和真实行为是否符合模型 |
| 线上复盘 | 真实玩家是否按假设参与、成长和消费 |

上层不能替代下层。线上胜率正常，可能只是两个实现错误互相抵消；表格结果正确，实机也可能因动作时间或目标选择不同而偏离。

## 2. 把设计目标写成可验证断言

“成长平滑”“战斗合理”无法自动检查。应转换为明确断言：

- 普通玩家第 7 天达到 40 级；
- 目标构筑对标准首领 TTK 位于 80—100 秒；
- 主要资源 28 天普通完成度为 70%—80%；
- 指定掉落 14 天内 P90 达成；
- 新旧版本累计资产迁移差额不超过最小计量单位；
- 任意合法配置下最终概率位于 0 到 1；
- 货币兑换闭环返回量不大于初始投入。

断言需要注明适用场景、玩家状态、配置版本和统计口径。目标变化时修改断言，而不是让测试结果悄悄偏离旧标准。

## 3. 公式和配置的基础检查

基础检查适合自动执行：

- 概率非负且权重归一；
- 等级、品质和 ID 引用存在；
- 成本、奖励和时间单位一致；
- 分段函数连接处连续或符合预期跳跃；
- 上下限和取整顺序正确；
- 配置没有循环引用和空值传播；
- 同一资产没有重复发放或重复扣除；
- 输入参数与计算结果分列存放。

对分段函数，在连接点 $L_b$ 检查左右值：

$$
\Delta_b=|f_{left}(L_b)-f_{right}(L_b)|
$$

若设计要求连续，则 $\Delta_b$ 应在允许误差内。还要比较左右斜率，避免数值连续但增长速度突然变化。

## 4. 黄金样例

黄金样例是一组人工确认过的输入和中间结果。它不追求覆盖所有情况，而用于证明核心链路没有被改坏。

伤害黄金样例可以记录：

```text
攻击与防御输入
→ 命中结果
→ 技能基础伤害
→ 防御减免
→ 暴击和格挡
→ 场景修正
→ 护盾与最终扣血
```

经济样例可以记录某玩家一天的玩法、奖励、升级选择和日终库存。成长样例可以记录某阶段从资源产出到模块完成度，再到最终属性和可通过内容。

样例必须保存中间值。只有输入和最终输出时，结果变化后仍无法定位是哪一步发生偏差。

## 5. 边界与极端组合

边界测试覆盖：

- 等级最低、最高和分段连接点；
- 资源为零、刚好足够和超过上限；
- 概率为零、接近零、接近一和必定发生；
- 防御、穿透、冷却和命中达到上下限；
- 战斗时间短于首次技能动作；
- 玩家缺少某个关键养成模块；
- 多个乘法系统同时达到上限；
- 迁移重复执行和中途失败后重试。

极端 Build 不等于不合法作弊配置。应先枚举系统允许玩家真实达到的组合，尤其关注多个单独合理的效果叠加后是否跨过阈值。

## 6. 批量模拟与分布

随机掉落、暴击、匹配、成长策略和多人战斗不能只看单次结果。模拟应报告：

- 均值、中位数和标准差；
- P10、P50、P90、P95 或 P99；
- 失败率、达成率和坏尾部；
- 不同玩家策略和完成度分层；
- 样本量、随机种子和置信误差。

固定种子用于版本回归，使相同随机序列下的差异可比较；多组种子用于评估真实分布。只运行一次随机模拟，无法区分规则变化和抽样波动。

## 7. 玩家策略模拟

数值模型常假设玩家平均投入所有系统，真实玩家却会优先升级高性价比或攻略推荐项目。成长和经济复盘至少模拟：

- 均衡投入；
- 输出优先；
- 生存优先；
- 囤积突破；
- 只做高效率玩法；
- 低活跃和错过限时内容；
- 回流追赶。

策略不是随意编造。上线前可以由策划和测试根据规则定义，发布后应从真实消费顺序和玩法路径中提取。若模拟只使用“理想玩家”，内容会对真实策略产生意外卡点。

## 8. 实机日志与模型对账

实机验证需要让程序输出模型能够识别的中间字段。战斗日志至少包含属性快照、技能 ID、命中判定、防御修正、暴击格挡、场景倍率、护盾和最终伤害；经济日志包含来源、去向、数量、库存前后值和关联系统。

对账流程：

1. 固定角色、目标、配置版本和随机种子；
2. 在策划模型中计算完整中间结果；
3. 实机执行同一操作并导出日志；
4. 逐字段比较首次差异；
5. 确认差异来自公式、顺序、取整、快照还是配置；
6. 修复后把该案例加入回归样例。

不要只比较最终伤害。两个中间错误可能碰巧得到相近结果，后续换一组输入就会暴露。

## 9. 试玩验证模型遗漏

模型会主动忽略一些变量，试玩用于发现这些遗漏。例如：

- 技能理论可用，但目标移动导致频繁未命中；
- TTK 合理，但受击峰值让玩家突然死亡；
- 玩法单位时间收益高，但排队和清包耗时未计入；
- 成长时间合理，但系统开放过密造成理解负担；
- 套装性能正常，但过渡阶段无法运行；
- 自动战斗和手动战斗使用完全不同的技能顺序。

试玩记录应区分规则问题、数值问题、操作反馈和内容理解。不能把所有负面体验都归因于数值，也不能用“手感问题”掩盖明确的时间和伤害偏差。

## 10. 上线指标先定义口径

指标必须明确事件、分母、时间窗口、玩家筛选和配置版本。例如“副本成功率”至少要说明：

- 以进入次数还是独立玩家为分母；
- 是否包含主动退出和断线；
- 首次挑战还是重复挑战；
- 按账号、角色还是队伍统计；
- 是否排除教学和异常样本；
- 使用哪个版本和难度。

同名指标口径不同，会得到完全不同结论。指标字典应记录计算公式、数据源、负责人和变更历史。

## 11. 从设计指标到诊断指标

设计指标描述是否达到目标，诊断指标解释为什么。

| 目标指标 | 诊断指标 |
|---|---|
| TTK | 有效 DPS、技能次数、命中率、输出占用率 |
| 通关率 | 失败时间、致死技能、剩余资源、玩家完成度 |
| 升级时间 | 各经验来源、参与率、体力溢出、主线卡点 |
| 养成完成度 | 日产出、消费顺序、库存、节点成本 |
| 掉落达成率 | 尝试次数、保底阶段、重复物、兑换使用 |
| 货币库存 | 来源、出口、毕业比例、交易与回收 |

只监控目标指标，发现异常后仍不知道改什么。每个目标至少准备一组能还原因果链的诊断字段。

## 12. 偏差定位

设计值与实测值的偏差可拆为：

$$
Observed-Target=InputError+RuleError+BehaviorGap+SamplingError+DataError
$$

- **输入错误**：目标玩家、产出、参与率或完成度假设不准；
- **规则错误**：公式、结算顺序、配置或实现不一致；
- **行为差异**：玩家没有按预设路径行动；
- **抽样误差**：样本太少或随机波动；
- **数据错误**：埋点缺失、重复、延迟或口径变化。

诊断时先验证数据和版本，再检查规则实现，最后讨论设计调整。直接根据一张异常图改参数，可能是在修复埋点错误。

## 13. 完整案例：首领 TTK 偏长

设计目标是普通阶段玩家在 90 秒击败首领，线上 P50 为 108 秒。按以下顺序拆解：

1. **玩家输入**：线上玩家攻击比模型低 6%，原因是技能模块完成度低于假设；
2. **循环表现**：实战输出占用率为 65%，模型使用 75%；
3. **命中表现**：主要技能命中率正常；
4. **首领规则**：阶段无敌总时间比设计表多 4 秒；
5. **数据口径**：线上 TTK 从进场开始，模型从首个可攻击帧开始。

这些偏差不能全部通过降低首领生命解决。可以分别修正技能资源产出、模型输出占用率、首领阶段时间和指标口径。若最后仍希望维持 90 秒，再调整生命。

这个过程说明复盘的输出不是“怪物血量降低 15%”，而是一份偏差来源及对应处理。

## 14. 版本回归

每次参数或规则修改都应记录：修改目标、影响变量、预期变化、护栏指标和回滚条件。回归集至少覆盖：

- 核心黄金样例；
- 等级和阶段连接点；
- 普通、高完成和缺失模块玩家；
- 主要职业和构筑；
- 资源产销与库存；
- 概率分布和保底状态；
- 历史玩家资产迁移；
- 新旧客户端或服务器兼容场景。

比较时不只看最终结果，还要看中间过程。最终 DPS 相同，资源循环和爆发窗口可能已经改变；平均库存相同，低活跃玩家可能更容易短缺。

## 15. A/B 测试的边界

A/B 测试适合比较可隔离的方案，但不能替代设计目标。实验前需确定：

- 主指标和护栏指标；
- 随机分组单位；
- 实验周期和样本量；
- 玩家间是否存在社交或市场污染；
- 多次查看结果是否抬高误判概率；
- 版本活动和渠道差异是否干扰。

经济、匹配和社交系统常存在组间污染：实验组价格或掉率会影响市场，队伍成员可能来自不同组。此时需要按服务器、队伍或市场单元分组，或采用准实验和分阶段发布。

统计显著不等于设计收益值得上线。还要比较效果大小、长期副作用、玩家公平感和回滚成本。

## 16. 工作簿与工具结构

建议建立：

1. 目标与断言；
2. 输入版本和配置快照；
3. 公式单元检查；
4. 黄金样例及中间值；
5. 边界和极端组合；
6. 批量模拟与随机种子；
7. 玩家策略复盘；
8. 实机日志对账；
9. 指标字典和数据质量；
10. 版本差异、护栏和回滚。

表格适合配置、单例和可视化；Python 等脚本适合批量模拟、自动回归和数据处理；数据库与 BI 适合线上观测。工具选择以可复现和团队可维护为准，不以复杂程度为目标。

## 17. 发布前检查

- [ ] 设计目标是否已经转换为可执行断言？
- [ ] 核心公式是否有单位、边界和配置引用检查？
- [ ] 是否保留包含中间值的黄金样例？
- [ ] 是否测试阶段连接点和合法极端组合？
- [ ] 随机系统是否报告分布而非只报告均值？
- [ ] 成长和经济是否模拟多种玩家策略？
- [ ] 实机是否能导出与模型对应的中间日志？
- [ ] 线上指标是否记录分母、窗口和配置版本？
- [ ] 异常处理是否先排除数据和实现错误？
- [ ] 每次修改是否有回归范围、护栏和回滚条件？

## 来源与核验说明

本文实际使用并重新组织了以下资料中的方法：

- 袁兆阳《游戏数值百宝书》第 5、8 章相关内容：成长复盘、战斗复盘、经济复盘及模型依赖；
- 明澈流风《游戏数值建模 V1.0》：最大模型测算、属性加载、PVE/PVP 模拟和表格—实机往返调试；
- 《游戏数值策划完全教程》第 12、14、17 章：指标口径、异常诊断、版本迁移、配置发布和工具链主题；
- 青云诀项目工作簿：跨表依赖、玩家成长、内容、产出和养成完成时间的实际连接结构；
- 本系列前四章：战斗、成长、经济和概率各自需要验证的目标与中间变量。

原资料中“复盘即可证明理论”等宽泛表述没有作为结论。复盘结果依赖模型覆盖、数据质量和玩家行为假设，只能提供受条件限制的证据。
