# 文章凝练与入库规范

## 一、基本目标

资料库不是“文章摘要库”，也不按外部文章的章节结构复制一套目录。

正确流程是：

```text
阅读原文
→ 拆出独立知识点
→ 判断价值与可信度
→ 放入资料库对应主题
→ 与库内已有内容合并
→ 将争议项交给维护者判断
→ 更新来源和变更记录
```

一篇外部文章可以被拆到多个目录；一个本地主题文档也可以吸收多个来源。资料来源保留在 `99_资料来源`，知识成果进入对应主题目录。

## 二、三层内容结构

### 1. 来源层

位置：`99_资料来源/`

记录原文标题、作者、链接、版本、阅读状态、版权边界和总体评价。来源层负责回答“信息从哪里来”，不承担完整知识讲解。

### 2. 判断层

位置：`00_索引与规范/待判断-主题或批次名称.md`；当前批次见[[待判断-第一批数值资料-J017-J023]]

记录无法直接确认的公式、案例、主张和删改建议。未经维护者判断，不把争议内容写成确定结论，也不静默删除可能有价值的内容。

### 3. 知识层

位置：`01`—`15` 的主题目录。

将核验后有价值的内容融合进主题文档。文章围绕一个设计问题组织，不围绕某个来源或原文章节组织。

## 三、拆分和归类规则

每个知识点只确定一个主要归属，必要时从其他目录建立链接，避免复制多份后逐渐不一致。

| 内容 | 主要目录 |
|---|---|
| 设计框架、选择、反馈、心流 | `01_基础理论` |
| 规则、资源、随机性、构筑、克制 | `02_玩法与机制` |
| 成长、装备、技能、进度、系统耦合 | `03_系统设计` |
| 伤害、属性、TTK、敌人、遭遇 | `04_战斗设计` |
| 经济、货币、概率、掉落、通胀、定价 | `05_数值与经济` |
| 地图、导航、节奏、空间 | `06_关卡与空间` |
| 剧情、任务、叙事选择 | `07_叙事与任务` |
| 心理、反馈、教程、界面、无障碍 | `08_玩家体验与UX` |
| 原型、试玩、实验方法 | `09_原型与测试` |
| 指标、埋点、运营、版本观测 | `10_数据与运营` |
| PVP、匹配、组队、公会、社交 | `11_多人与社交` |
| Bot、ML、PCG、动态难度 | `12_AI与程序化生成` |
| 某一游戏类型的专属规律 | `13_品类专题` |
| 工具链、配置、发布、迁移、协作 | `14_制作与协作` |
| 具体游戏分析 | `15_游戏拆解` |

## 四、什么必须保留

凝练时优先保留原文中最难替代的信息：

1. **关键问题**：这条知识解决什么设计问题。
2. **因果关系**：为什么采用该设计会导致某种行为或体验。
3. **可执行方法**：步骤、变量、决策条件和检查方式。
4. **公式及假设**：变量定义、单位、边界、取整和适用前提。
5. **高信息量案例**：能证明、反驳或限定结论的具体案例。
6. **反例和失败条件**：方法在什么情况下无效。
7. **生产约束**：成本、依赖、风险、上线和回滚要求。
8. **独到观点**：来源中不容易从常识推导出的有效判断。
9. **来源锚点**：重要结论能追溯到原文或其他证据。

删掉这些内容后只剩“要平衡体验与数值”之类的话，就说明凝练失败。

## 五、什么可以删除

满足以下条件时，可以不进入知识层，但应在来源卡保留必要说明：

- 重复表达，且没有新增条件、例子或推导；
- 与主题无关的铺垫、宣传和情绪化修辞；
- 只罗列名词，没有解释关系和使用方法；
- 已被更准确、更完整的内容覆盖；
- 明显过时，并且对理解历史没有帮助；
- 无来源的宽泛结论，且不能通过逻辑或案例支撑；
- 为了显得专业而增加、实际不帮助决策的复杂公式；
- 默认模板、占位内容和与作者观点无关的生成页面。

## 六、什么不能擅自删除或改写

以下内容必须进入“待判断清单”，由维护者决定。待判断项不能只写抽象类别；必须列出具体公式、参数、游戏案例或原文句意，并标注来源章节、原文主张和存疑原因：

- 可能错误，但尚未找到足够证据的公式或结论；
- 与维护者设计经验可能冲突的行业判断；
- 有实践价值，但可能只适用于特定品类的经验；
- 涉及商业化伦理、玩家操纵或价值立场的建议；
- 原文独有但证据较弱的观点；
- 删除后可能改变作者原意的关键前提；
- 多个可靠来源之间相互矛盾的结论。

处理选项统一为：

- `保留为结论`
- `保留但限定范围`
- `保留为争议观点`
- `移入案例或历史备注`
- `删除`
- `等待更多证据`

## 七、单个知识点的写法

每个进入主题文档的知识点，尽量采用以下结构：

```markdown
## 知识点标题

### 解决的问题

### 核心结论

### 为什么成立

### 使用方法或计算过程

### 适用条件

### 失败情况与反例

### 来源与判断
- 原文观点：……
- 本库整理：……
- 可信状态：已核验 / 待判断 / 需复查
```

不是每段都要机械展示标题，但信息不能被压缩掉。

## 八、合并规则

当主题文档已经存在时：

1. 先比较新知识点与已有内容。
2. 完全重复：只增加来源，不重复正文。
3. 补充条件：合并到已有结论的适用范围。
4. 提供反例：加入失败条件或争议部分。
5. 发生冲突：不覆盖旧观点，加入待判断清单。
6. 形成新问题：新建主题文档，并从原文档链接过去。

## 九、语言与行文规范

正式知识文章采用偏教材式语言，而不是宣传文案、演讲提纲或聊天式摘要。

### 1. 推荐写法

- 先定义概念和变量，再说明它们之间的关系。
- 按“问题背景—概念解释—推导过程—示例—适用边界—练习或检查”的顺序展开。
- 使用完整段落解释因果关系，不依赖大量短句和清单代替论证。
- 公式前说明为什么需要该公式，公式后解释结果代表什么。
- 案例需要交代游戏类型、规则环境和观察条件，不能只报游戏名。
- 专业术语第一次出现时给出中文解释；必要时保留英文原词。
- 结论应由前文自然推出，避免突然宣布一个未经证明的原则。
- 可以使用表格、流程图和检查表，但它们用于辅助正文，不能取代正文。
- 对尚无定论的内容使用“在……条件下”“通常”“可能”等准确限定语。
- 保持平实、克制和可复查，不刻意追求金句感。

### 2. 避免的 AI 式表达

- 避免连续使用“不是……而是……”“真正的……是……”等模板句。
- 避免每节都用一句口号或金句收尾。
- 避免没有解释的三段式排比和密集短句。
- 避免“这很重要”“需要注意的是”“本质上”等空泛过渡语反复出现。
- 避免把常识包装成结论，例如“设计需要兼顾体验和数值”。
- 避免滥用引号、破折号、冒号和粗体制造虚假重点。
- 避免为了显得完整而机械罗列固定数量的步骤、原则或维度。
- 避免拟人化、夸张比喻和与知识无关的俏皮话进入正式正文。
- 避免把来源摘要改写几遍后伪装成独立推导。

### 3. 教材式段落示例

不推荐：

> 数值设计不是填表，而是设计关系。好的数值不是算出来的，而是验证出来的。

推荐：

> 数值表记录的是参数，但参数本身不能说明系统是否成立。设计者还需要说明参数之间的计算顺序、参数变化对玩家行为的影响，以及这些影响如何通过测试或线上数据验证。因此，数值设计至少包含建模、标定和验证三个相互衔接的环节。

不推荐：

> 随机性不是制造惊喜，而是管理期待。

推荐：

> 随机掉落会使不同玩家经历不同的获得过程。设计时除单次掉落概率外，还需要计算累计获得概率、达成目标所需次数的分布和连续失败概率。保底机制的作用，是限制分布的坏尾部，使玩家能够估计完成目标所需的最高成本。

### 4. 文章完成后的语言检查

- [ ] 仅阅读正文，读者能否理解概念之间的推导关系？
- [ ] 删除口号式句子后，文章是否损失实际信息？若没有，应直接删除。
- [ ] 每个公式是否解释了变量、前提和结果？
- [ ] 每个结论是否能在前文找到证据或推导？
- [ ] 清单是否有正文解释，而不是孤零零地堆在页面上？
- [ ] 是否存在明显重复的句式和套路化收尾？
- [ ] 行文是否接近教材或专业手册，而不是营销文章和 AI 对话？

## 十、质量门槛

正式标记为 `已提炼` 前，至少满足：

- [ ] 已完成全文阅读，而不是只看目录或摘要
- [ ] 已拆到正确主题，不照搬来源章节
- [ ] 保留关键方法、推导、案例和边界
- [ ] 删除内容有明确理由
- [ ] 存疑内容已进入待判断清单
- [ ] 外部观点、本库判断和维护者观点可以区分
- [ ] 重要公式可以解释变量和前提
- [ ] 文章可以独立帮助一次设计决策
- [ ] 来源可追溯，没有大段改写式转载

## 十一、当前教程的处理原则

《游戏数值策划完全教程》的 17 章只作为来源结构，不作为本库文章结构。

- 第 1—4 章已经形成的主题文章全部重新进入复核状态。
- 第 5—17 章合并提纲仅作为临时知识地图，不算正式凝练成果。
- 后续按知识点拆入经济、概率、商业化、多人、数据、AI、版本、心理、品类和工具链目录。
- 任何准备删除或判错的内容先进入待判断清单，由维护者决定。
