# 数值工作簿设计：输入、计算、输出与检查

工作簿既是计算工具，也是团队理解数值规则的接口。参数、公式、配置和验证混在一页时，修改难以审查，错误也难追踪。

## 1. 四层结构

```text
Inputs → Calculations → Outputs → Checks
```

Inputs 只放可调整参数及单位；Calculations 保存中间过程；Outputs 生成配置和图表；Checks 放断言、差异和异常。人工覆盖应单独记录值、原因和负责人。

## 2. 参数字典

每个参数记录 ID、名称、类型、单位、默认值、范围、所属系统、来源、负责人和版本。概率、百分比、万分比和秒毫秒不能只靠列名猜测。

参数应区分设计输入、外部引用和计算结果。颜色只能辅助，不能作为唯一语义。

## 3. 引用方向

建立单向依赖，避免循环引用和跨文件隐式链接。公共基准集中维护，具体系统只读取，不复制。依赖图用于评估修改传播。

跨表引用应通过稳定 ID，而不是依赖容易变化的行列位置。删除或插入行后仍需通过引用检查。

## 4. 配置生成

输出表与服务器 Schema 对齐，检查必填、唯一键、枚举、范围和引用。不要让程序复制策划表中的公式再实现一遍；明确哪一侧是权威，并通过黄金样例对账。

生成过程应可重复执行，同一版本输入得到相同输出。导出文件附带版本、时间和校验值。

## 5. 可视化

图表用于观察曲线、阶段跳点、分布和版本差异。不要只画平滑总曲线，还要显示逐级时间、累计投入、分位数和异常点。图表注明单位、玩家层和配置版本。

## 6. 自动检查

至少包含概率归一、ID 引用、负值、上限、分段连接、预算总和、产销缺口、资产对账和旧版差异。错误应指向具体行、字段和规则。

关键检查以明确 PASS/FAIL 输出，不要求评审者肉眼扫描整张表。

## 7. 大表拆分

结构庞大时，将参数、生成数据和查询工具分开。查询页允许输入等级、品质、角色或版本，返回关键结果，避免团队在几千行数据中手动查找。

拆表后仍要保留总入口、依赖和生成顺序。文件越多不代表模块化越好，跨文件引用失控同样危险。

## 8. 协作与版本

首页说明用途、输入区、生成步骤、依赖文件和更新时间。锁定公式区，区分草稿、评审和发布版本。重要修改通过版本控制或导出语义差异评审。

工作簿交接应包含黄金样例、已知限制、手工步骤和故障恢复方式，不能只交一个能运行但没人敢改的文件。

## 9. 推荐目录示例

```text
00_README
01_参数字典
02_公共基准
10_系统输入
20_中间计算
30_配置输出
40_黄金样例
50_边界检查
60_版本差异
```

README 记录生成顺序和依赖。公共基准只维护一份，系统表通过稳定 ID 读取。版本差异页将单元格变化转成 TTK、完成时间和资源总量等业务变化。

## 10. 故障定位

结果异常时先检查输入版本，再检查引用和单位，然后检查公式与取整，最后检查人工覆盖。若工作簿无法指出某个结果来自哪些参数，就需要补充公式追踪或中间输出。

## 发布前检查

- [ ] 输入、计算、输出和检查是否分层？
- [ ] 参数是否有类型、单位和范围？
- [ ] 公共基准是否集中维护？
- [ ] 配置能否自动校验和重复生成？
- [ ] 新旧版本能否查看语义差异？
