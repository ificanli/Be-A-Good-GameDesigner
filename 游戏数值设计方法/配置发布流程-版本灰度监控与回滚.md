# 配置发布流程：版本、灰度、监控与回滚

数值配置进入线上后会影响战斗、经济和玩家资产。安全发布的目标不是“把表推上去”，而是让每个改动可识别、可验证、可观测，并在异常时安全暂停、回滚或补偿。

## 1. 冻结版本并完成校验材料

### 1.1 版本冻结

当本次改动已经进入发布候选状态时，先冻结输入。冻结对象包括配置、规则代码、迁移脚本、生成参数、适用客户端、适用服务器和灰度范围。冻结后不要再用“顺手改一个数”绕过流程；任何新增改动都重新生成一个候选版本。

发布记录至少包含这些字段：配置版本、规则代码版本、迁移脚本版本、适用客户端、适用服务器、变更人、审批人、变更原因、影响范围、冻结时间和回滚目标版本。运行日志也要携带配置版本，否则事故发生后无法解释跨版本数据。

配置、规则代码和迁移脚本分别版本化，并记录兼容关系。只保存最终 Excel 文件不足以重建线上状态，因为线上结果还取决于生成规则、迁移顺序和客户端兼容窗口。

本步完成后，你应能回答三个问题：这次发什么版本，哪些客户端和服务器能读它，失败时回到哪个版本。

### 1.2 自动校验

只有冻结版本可以进入自动校验。校验对象必须来自同一个候选版本，不能把新配置、旧规则代码和未冻结脚本拼在一起验证。

自动校验至少覆盖 Schema、引用、范围、概率、黄金样例、边界、批量回归、模拟结果、客户端兼容和资产迁移。高风险改动还要加入生产快照演练和性能测试。这里的“高风险”包括会改变玩家资产、掉落概率、付费价值、赛季进度、跨服交易或排行榜结果的改动。

门禁失败必须阻止发布。不要把阻断条件改成提醒，也不要依赖“这次先手动确认”。如果确实需要临时豁免，记录豁免人、原因、风险、影响范围、补测计划和失效时间，并让审批人在评审中看到这些信息。

边界检查要覆盖最小值、最大值、空引用、重复 ID、概率和不为 1、负产出、循环引用、客户端未知字段、迁移重复执行和回滚后再迁移。自动校验不能证明设计一定正确，但能阻止已知错误进入评审。

### 1.3 生成发布材料

自动校验通过后，生成发布材料。发布材料不是截图集合，而是让评审者判断“能不能发”的证据包。

发布材料包含改动目的、字段级差异、语义差异、黄金样例结果、批量回归结果、模拟结果、资产迁移影响、灰度计划、监控指标、护栏阈值和回滚方案。大量自动生成行的差异不要逐行堆给评审者，要汇总为业务指标，例如角色伤害变化、玩家完成时间变化、货币净流量变化和需要迁移的资产数量。

语义差异要说明改动会怎样影响玩家体验。战斗配置说明 TTK、胜率、伤害峰值和异常伤害；经济配置说明产出、消耗、库存和套利路径；概率配置说明实际概率、保底进度、期望产出和投诉风险。

如果材料无法解释某个高风险字段的影响，不要进入评审。先补模拟、补样例或缩小发布范围。

## 2. 评审发布并执行灰度

### 2.1 评审发布决定

评审只评审已经冻结并通过自动校验的候选版本。评审会议开始前，评审人应拿到同一份发布材料；会议中不要临时替换配置文件。

评审按这个顺序进行：先确认变更目的，再看影响路径，然后检查黄金样例和模拟结果，最后确认灰度、监控和回滚。评审结论只能是通过、驳回或带豁免通过。带豁免通过时，必须写明豁免项、补测时间和更严格的灰度阈值。

评审需要保留一个不能直接套用本流程的边界：当配置发布与代码热修、数据库结构变更或外部平台规则变更绑定时，单独通过配置评审不代表可以上线。此时发布决策要合并到更大的变更流程中。

评审通过后，锁定发布窗口、执行人、观察人和回滚触发人。没有明确回滚触发人时，不要开始灰度。

### 2.2 灰度发布

灰度从最小可观察范围开始。常见顺序是内部环境、测试服、少量服务器或少量玩家群，再逐步扩大。选择灰度组时要考虑社交、匹配和交易污染；如果新旧配置的玩家会直接交易或同场匹配，灰度范围要改成服务器、赛季或经济域，而不是随机抽玩家。

开始灰度前，先写下继续、暂停和回滚阈值。阈值要使用发布材料中的目标指标和护栏指标，不能上线后临时挑选对自己有利的指标。

灰度时间要覆盖目标行为周期。每日养成至少观察一个完整日循环；周活动、赛季结算和跨服市场需要覆盖对应周期。观察窗口未结束前，不要只因为短期均值正常就扩大范围。

每次扩大灰度前，执行人确认三件事：系统健康没有异常，目标指标方向符合预期，护栏指标没有越界。任一条件不满足，先暂停扩大，再决定继续观察、修正后重发或回滚。

## 3. 监控结果并处置回滚

### 3.1 监控发布结果

监控从灰度开始前就要就绪。发布后同时看系统健康、目标指标和护栏指标，不要只看服务是否报错。

监控必须按配置版本、玩家层、服务器、模式和灰度批次分层。新旧配置混在一起求平均，可能把异常稀释成正常。战斗改动观察 TTK、胜率、异常伤害和失败率；经济改动观察产销、库存、价格、套利和净流量；概率改动观察实际概率、保底进度、稀有物产出和投诉。

当目标指标变化符合预期但护栏指标越界时，优先保护生产安全。比如新掉落配置提高了活动参与率，却让稀有物产出超过阈值，应暂停扩大或回滚，而不是把参与率当作继续发布的理由。

监控结论要写回发布记录。记录包括观察时间、配置版本、灰度范围、异常指标、处置动作和下一次检查时间。

### 3.2 回滚与补偿

触发回滚条件时，先停止扩大灰度，再按预案执行。不要在事故中临时决定“只改回几个字段”，除非评审过这个修复版本并确认兼容关系。

规则、配置和玩家数据回滚要分开处理。配置回滚不一定能撤销已经产生的资产；数据回滚也不能覆盖发布后玩家的合法进展。使用迁移账本和补偿事务处理不可逆结果，并保留对账记录。

回滚方案要明确触发人、执行顺序、兼容窗口、数据对账、玩家通知和恢复发布条件。执行顺序通常是冻结相关入口，切回配置或规则版本，处理迁移或补偿，对账玩家资产，观察护栏指标，最后决定是否重新发布。

如果回滚会破坏客户端兼容、删除玩家合法进度或造成更大经济污染，不要默认整库回档。先隔离影响范围，再选择保留、回收、补偿或延迟修复。

## 4. 复盘沉淀与发布门禁

### 4.1 事故复盘

发布完成后，无论全量成功还是回滚，都要把结果写入记录。发生事故时，复盘记录时间线、影响范围、触发条件、检测缺口、处置动作、玩家影响、长期修复和负责人。

复盘目标是更新门禁、监控和回归集，而不是只追究谁填错数字。若事故来自掉落概率配置，后续修复不应只改回权重，还要补概率和校验、稀有物产出护栏、黄金样例和资产对账检查。

事故复盘完成后，关闭本次发布。若还要发布修复配置，从“版本冻结”重新开始，不要把复盘中的临时修改直接推向全量。

### 4.2 发布清单示例

```text
版本冻结
→ 自动校验
→ 生产快照演练
→ 生成发布材料
→ 评审
→ 灰度
→ 监控
→ 全量或回滚
→ 对账与事故复盘
```

### 4.3 事故示例

若掉落权重错误导致稀有物多发，简单回滚配置只能阻止继续产出，不能处理已经获得和交易的资产。处置需冻结相关交易、统计来源、评估是否回收或保留、执行补偿并对账。方案取决于影响和玩家信任，不能默认整库回档。

这个案例保留在文中，是因为它说明配置回滚和数据处置不是同一件事。读者不能把“恢复旧配置”当成事故结束，也不能把数据库回档当成默认答案。

### 4.4 发布前门禁

- [ ] 冻结记录是否包含配置版本、代码版本、迁移脚本版本、适用范围、变更人、审批人、原因和回滚目标版本？
- [ ] 配置、规则代码和迁移脚本是否分别版本化，并记录兼容关系？
- [ ] 自动校验是否覆盖 Schema、引用、范围、概率、黄金样例、边界、模拟和资产迁移？
- [ ] 门禁失败是否会真正阻止发布，而不是只发提醒？
- [ ] 发布材料是否生成业务语义差异，而不是只比较单元格？
- [ ] 灰度分组是否避免社交、匹配和市场污染？
- [ ] 继续、暂停和回滚阈值是否在上线前写入发布材料？
- [ ] 监控是否按配置版本、玩家层、模式和灰度批次分层？
- [ ] 回滚方案是否处理已经产生的玩家资产、合法进度和补偿对账？
- [ ] 事故复盘是否会更新门禁、监控和回归集？
