# 数值验证与数据复盘：从离线模型到线上诊断

数值表能够算出结果，不代表结果符合设计目标。公式可能写错，输入可能过期，模型可能遗漏玩家行为，实机实现也可能与策划表不同。上线后，真实参与率、操作方式和消费策略还会继续拉开设计假设与结果之间的距离。

这篇文章只解决一个工作问题：当团队要证明一套数值方案是否成立，或要解释线上指标为什么偏离目标时，怎样把目标、规则、数据、诊断和决策连成一条可复查的链。单个平均值、一次试玩或一张异常图都不能单独完成这个任务。

## 1. 先把目标变成可验证断言

验证从设计目标开始，而不是从工具开始。“成长平滑”“战斗合理”无法自动检查，必须改写成带场景、玩家状态、版本和口径的断言。例如：普通玩家第 7 天达到 40 级；目标构筑对标准首领 TTK 位于 80—100 秒；主要资源 28 天普通完成度为 70%—80%；指定掉落 14 天内 P90 达成；新旧版本累计资产迁移差额不超过最小计量单位；任意合法配置下最终概率位于 0 到 1；货币兑换闭环返回量不大于初始投入。

断言决定后续证据。若目标构筑、普通玩家或统计窗口改变，应修改断言本身，而不是让测试结果悄悄偏离旧标准。每条断言都要指向一类证据：公式能证明单位和边界，黄金样例能证明核心链路，批量模拟能证明分布，实机日志能证明实现一致，线上数据能证明真实玩家是否按假设行动。

完整验证链如下：

```text
公式与配置检查
→ 黄金样例
→ 批量模拟与分布
→ 实机试玩与日志对账
→ 线上数据与版本复盘
```

这五层不能互相替代。线上胜率正常，可能只是两个实现错误互相抵消；表格结果正确，实机也可能因为动作时间或目标选择不同而偏离。验证计划应先说明每层回答什么问题。

| 层级 | 主要问题 |
|---|---|
| 公式与配置 | 公式、单位、引用、边界和概率是否正确 |
| 黄金样例 | 典型输入能否得到人工确认的结果 |
| 批量模拟 | 随机、策略和玩家分层会形成什么分布 |
| 实机试玩 | 动作、界面、AI 和真实行为是否符合模型 |
| 线上复盘 | 真实玩家是否按假设参与、成长和消费 |

## 2. 用离线证据证明规则没有先错

离线验证先排除规则层错误。基础检查适合自动执行：概率非负且权重归一；等级、品质和 ID 引用存在；成本、奖励和时间单位一致；分段函数连接处连续或符合预期跳跃；上下限和取整顺序正确；配置没有循环引用和空值传播；同一资产没有重复发放或重复扣除；输入参数与计算结果分列存放。

对分段函数，在连接点 $L_b$ 检查左右值：

$$
\Delta_b=|f_{left}(L_b)-f_{right}(L_b)|
$$

若设计要求连续，则 $\Delta_b$ 应在允许误差内。还要比较左右斜率，避免数值连续但增长速度突然变化。这里的决策不是“通过或失败”这么简单：若跳跃来自明确设计，就把它写入断言；若跳跃来自表格错误，就进入修复和回归。

黄金样例接在基础检查之后。它是一组人工确认过的输入和中间结果，不追求覆盖所有情况，而用于证明核心链路没有被改坏。伤害黄金样例可以记录：

```text
攻击与防御输入
→ 命中结果
→ 技能基础伤害
→ 防御减免
→ 暴击和格挡
→ 场景修正
→ 护盾与最终扣血
```

经济样例可以记录某玩家一天的玩法、奖励、升级选择和日终库存。成长样例可以记录某阶段从资源产出到模块完成度，再到最终属性和可通过内容。样例必须保存中间值；只有输入和最终输出时，结果变化后仍无法定位是哪一步发生偏差。

边界测试要覆盖等级最低、最高和分段连接点，资源为零、刚好足够和超过上限，概率为零、接近零、接近一和必定发生，防御、穿透、冷却和命中达到上下限，战斗时间短于首次技能动作，玩家缺少某个关键养成模块，多个乘法系统同时达到上限，以及迁移重复执行和中途失败后重试。极端 Build 不等于不合法作弊配置；应先枚举系统允许玩家真实达到的组合，尤其关注多个单独合理的效果叠加后是否跨过阈值。

## 3. 用模拟检查分布和玩家策略

随机掉落、暴击、匹配、成长策略和多人战斗不能只看单次结果。模拟报告至少包含均值、中位数和标准差，P10、P50、P90、P95 或 P99，失败率、达成率和坏尾部，不同玩家策略和完成度分层，以及样本量、随机种子和置信误差。

固定种子用于版本回归，使相同随机序列下的差异可比较；多组种子用于评估真实分布。只运行一次随机模拟，无法区分规则变化和抽样波动。若目标是“指定掉落 14 天内 P90 达成”，平均达成天数并不能证明目标成立，必须看 P90 和坏尾部。

成长和经济还要模拟玩家策略。数值模型常假设玩家平均投入所有系统，真实玩家却会优先升级高性价比或攻略推荐项目。上线前可以由策划和测试定义均衡投入、输出优先、生存优先、囤积突破、只做高效率玩法、低活跃和错过限时内容、回流追赶等策略；发布后应从真实消费顺序和玩法路径中提取策略。若模拟只使用“理想玩家”，内容会对真实策略产生意外卡点。

## 4. 把模型带到实机里对账

离线模型通过后，要证明实机和模型算的是同一件事。程序需要输出模型能够识别的中间字段。战斗日志至少包含属性快照、技能 ID、命中判定、防御修正、暴击格挡、场景倍率、护盾和最终伤害；经济日志包含来源、去向、数量、库存前后值和关联系统。

对账按固定角色、目标、配置版本和随机种子开始。先在策划模型中计算完整中间结果，再让实机执行同一操作并导出日志，然后逐字段比较首次差异，确认差异来自公式、顺序、取整、快照还是配置。修复后，把该案例加入回归样例。

不要只比较最终伤害。两个中间错误可能碰巧得到相近结果，后续换一组输入就会暴露。

试玩用于发现模型主动忽略的变量。例如：技能理论可用，但目标移动导致频繁未命中；TTK 合理，但受击峰值让玩家突然死亡；玩法单位时间收益高，但排队和清包耗时未计入；成长时间合理，但系统开放过密造成理解负担；套装性能正常，但过渡阶段无法运行；自动战斗和手动战斗使用完全不同的技能顺序。试玩记录应区分规则问题、数值问题、操作反馈和内容理解，不能把所有负面体验都归因于数值，也不能用“手感问题”掩盖明确的时间和伤害偏差。

## 5. 上线前先定义数据口径

线上复盘的第一步不是看图，而是确认指标口径。以“副本成功率”为例，至少要说明以进入次数还是独立玩家为分母，是否包含主动退出和断线，统计首次挑战还是重复挑战，按账号、角色还是队伍统计，是否排除教学和异常样本，以及使用哪个版本和难度。

同名指标口径不同，会得到完全不同结论。指标字典应记录计算公式、数据源、负责人和变更历史。每个目标指标还要准备诊断指标，否则发现异常后仍不知道改什么。

| 目标指标 | 诊断指标 |
|---|---|
| TTK | 有效 DPS、技能次数、命中率、输出占用率 |
| 通关率 | 失败时间、致死技能、剩余资源、玩家完成度 |
| 升级时间 | 各经验来源、参与率、体力溢出、主线卡点 |
| 养成完成度 | 日产出、消费顺序、库存、节点成本 |
| 掉落达成率 | 尝试次数、保底阶段、重复物、兑换使用 |
| 货币库存 | 来源、出口、毕业比例、交易与回收 |

A/B 测试也必须服务于已定义的目标。实验前需确定主指标和护栏指标、随机分组单位、实验周期和样本量、玩家间是否存在社交或市场污染、多次查看结果是否抬高误判概率、版本活动和渠道差异是否干扰。经济、匹配和社交系统常存在组间污染：实验组价格或掉率会影响市场，队伍成员可能来自不同组。此时需要按服务器、队伍或市场单元分组，或采用准实验和分阶段发布。统计显著不等于设计收益值得上线，还要比较效果大小、长期副作用、玩家公平感和回滚成本。

## 6. 按偏差来源诊断，而不是直接改数值

设计值与实测值的偏差可拆为：

$$
Observed-Target=InputError+RuleError+BehaviorGap+SamplingError+DataError
$$

其中，**输入错误**指目标玩家、产出、参与率或完成度假设不准；**规则错误**指公式、结算顺序、配置或实现不一致；**行为差异**指玩家没有按预设路径行动；**抽样误差**指样本太少或随机波动；**数据错误**指埋点缺失、重复、延迟或口径变化。

诊断顺序应先验证数据和版本，再检查规则实现，随后判断行为差异和输入假设，最后讨论设计调整。直接根据一张异常图改参数，可能是在修复埋点错误。

一个首领 TTK 复盘能说明这条链。设计目标是普通阶段玩家在 90 秒击败首领，线上 P50 为 108 秒。拆解后发现：线上玩家攻击比模型低 6%，原因是技能模块完成度低于假设；实战输出占用率为 65%，模型使用 75%；主要技能命中率正常；阶段无敌总时间比设计表多 4 秒；线上 TTK 从进场开始，模型从首个可攻击帧开始。

这些偏差不能全部通过降低首领生命解决。可以分别修正技能资源产出、模型输出占用率、首领阶段时间和指标口径。若最后仍希望维持 90 秒，再调整生命。复盘的输出不是“怪物血量降低 15%”，而是一份偏差来源及对应处理。

## 7. 修改后用回归和工作簿收口

每次参数或规则修改都应记录修改目标、影响变量、预期变化、护栏指标和回滚条件。回归集至少覆盖核心黄金样例，等级和阶段连接点，普通、高完成和缺失模块玩家，主要职业和构筑，资源产销与库存，概率分布和保底状态，历史玩家资产迁移，以及新旧客户端或服务器兼容场景。

比较时不只看最终结果，还要看中间过程。最终 DPS 相同，资源循环和爆发窗口可能已经改变；平均库存相同，低活跃玩家可能更容易短缺。

工作簿建议按验证链组织：目标与断言，输入版本和配置快照，公式单元检查，黄金样例及中间值，边界和极端组合，批量模拟与随机种子，玩家策略复盘，实机日志对账，指标字典和数据质量，版本差异、护栏和回滚。表格适合配置、单例和可视化；Python 等脚本适合批量模拟、自动回归和数据处理；数据库与 BI 适合线上观测。工具选择以可复现和团队可维护为准，不以复杂程度为目标。

## 发布前检查

- [ ] 设计目标是否已经转换为可执行断言？
- [ ] 核心公式是否有单位、边界和配置引用检查？
- [ ] 是否保留包含中间值的黄金样例？
- [ ] 是否测试阶段连接点和合法极端组合？
- [ ] 随机系统是否报告分布而非只报告均值？
- [ ] 成长和经济是否模拟多种玩家策略？
- [ ] 实机是否能导出与模型对应的中间日志？
- [ ] 线上指标是否记录分母、窗口和配置版本？
- [ ] 异常处理是否先排除数据和实现错误？
- [ ] 每次修改是否有回归范围、护栏和回滚条件？

本文实际使用并重新组织了以下资料中的方法：

- 袁兆阳《游戏数值百宝书》第 5、8 章相关内容：成长复盘、战斗复盘、经济复盘及模型依赖；
- 明澈流风《游戏数值建模 V1.0》：最大模型测算、属性加载、PVE/PVP 模拟和表格—实机往返调试；
- 《游戏数值策划完全教程》第 12、14、17 章：指标口径、异常诊断、版本迁移、配置发布和工具链主题；
- 青云诀项目工作簿：跨表依赖、玩家成长、内容、产出和养成完成时间的实际连接结构；
- 本系列前四章：战斗、成长、经济和概率各自需要验证的目标与中间变量。

原资料中“复盘即可证明理论”等宽泛表述没有作为结论。复盘结果依赖模型覆盖、数据质量和玩家行为假设，只能提供受条件限制的证据。
