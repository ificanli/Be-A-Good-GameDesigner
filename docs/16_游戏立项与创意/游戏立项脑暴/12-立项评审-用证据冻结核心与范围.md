# 12 · 立项评审：用证据冻结核心与范围

立项评审不是选择分数最高的创意，也不是确认策划案已经写得足够完整。它要判断当前证据是否支持进入更昂贵的开发阶段，并明确下一阶段冻结什么、继续验证什么、在什么条件下停止。

## 立项包应包含的材料

### 一页产品定义

写明目标用户、平台、单局时长、体验承诺、主要输入、胜负条件和产品目的。任何评审者应能从这一页知道项目准备提供什么体验。

### 玩家动词与核心因果

```text
玩家反复做什么
→ 对象发生什么变化
→ 留下什么局面
→ 为什么下一次选择不同
```

这部分用来防止系统名称掩盖实际操作。若动词链主要是点击领取、等待与整理，需要解释乐趣从何产生。

### 假设与证据表

| 假设 | 当前证据 | 证据等级 | 未知项 | 下一步 |
|---|---|---|---|---|
|  |  | 主张/实现/观察/复现 |  |  |

《弹射梭哈》可以把弹射手感列为试玩观察支持，把两小时目标曲线列为尚未验证。把不同成熟度写在一张表上，比笼统标记“核心通过”更准确。

### 风险与生产范围

列出体验、技术、内容和商业风险，附最低验证方法。范围分为当前阶段必须完成、核心通过后再做和明确不做。还要估算内容生产模式：主要依赖规则组合、程序生成还是手工关卡。

### 查重与市场位置

记录最相近产品、相同高频操作和本方案新增判断。市场数据可以说明用户与竞争环境，不能替代核心玩法证据。

## 评审使用门槛，不使用平均分掩盖短板

加权评分可以帮助排序，却不应让美术表现和商业空间抵消核心决策不足。建议设置硬门：

- 玩家能理解主要输入和目标；
- 核心动作有即时反馈；
- 至少存在两个理由不同的选择；
- 当前选择会改变未来局面；
- 失败可以归因；
- 核心能够在预算内实现；
- 未知风险有明确验证计划。

任一核心门未过，结论应是继续验证或返工，而不是用总分批准立项。

## 四种评审结论

### 进入下一阶段

核心证据达到当前门槛，范围与风险可控。批准的是下一阶段预算，不是保证最终成功。

### 附条件通过

部分证据成立，但必须先完成指定验证。例如只有在三名首玩者能理解组件顺序后，才允许《贪吃蛇军火库》扩充更多组件。

### 返回原型

主要未知项仍能以较低成本验证，或测试受到实现问题污染。需要明确返回后只解决哪些问题。

### 停止

核心假设被否定、成本不可接受或差异不足。停止结论应保存证据与可回收知识，避免同一方案换名字再次进入候选池。

## 冻结核心，不冻结所有细节

立项后应冻结三至五条核心不变量，例如：

- 数字球必须通过真实碰撞进入组合；
- 特殊墙只加工实际撞墙的激活球；
- 矿洞取牌必须受遮挡关系约束；
- 武器必须可见地沿蛇身加工并从尾部释放。

数值、内容数量、界面布局和具体表现可以继续迭代。若开发发现核心不变量无法成立，应触发重新评审，而不是静默改变产品。

## 下一阶段目标必须仍然是证据

立项后也不能立刻把计划改成功能清单。阶段目标应写成：

```text
让首玩者在一分钟内独立完成核心闭环；
让三种玩家策略都能完成一局并产生不同代价；
验证十个组件能否形成至少三条规则不同的构筑；
验证目标设备上连续十次重开无阻断问题。
```

功能只是取得这些证据的手段。阶段结束时，根据证据再次决定扩大、修正或停止。

## 示例：评审结论怎样写

假设某候选的核心输入已经稳定，三名首玩者能在一分钟内完成闭环，其中两人主动使用关键机制，但长线组件关系和目标设备性能尚未验证。合适结论是“附条件进入四周预制作”：第一周验证十个组件的交叉关系与移动端性能，未达到门槛则返回原型。不能写成笼统的“创意好，建议立项”。

结论还应指定负责人、版本与复审日期。没有时间点的附条件通过，往往会在开发中自动变成正式通过。

## 评审会议的顺序

1. 先演示未剪辑的真实玩法，不先讲愿景；
2. 由测试负责人陈述观察与反证；
3. 设计者解释核心因果和修改历史；
4. 制作岗位评估技术与内容风险；
5. 对照硬门逐项作结论；
6. 最后才讨论市场、商业和扩展机会；
7. 记录不同意见与需要补证的项目。

这样可以减少完整提案和演示包装对核心证据的遮蔽。

